## 一、Shadowsocks 下线根因

### 代码和历史证据

P1 合入前的历史提交 `81ed942` 标题是 `fix(access)!: enforce explicit grants and retire Shadowsocks`。提交说明明确写出以下决策。

- 普通节点改为只允许显式授权。
- 删除最后一个授权后停用受影响客户。
- 按“操作者确认没有 SS 消费者”的产品决定退役 Shadowsocks。
- 升级前要求旧 SS 节点迁移到 VLESS/Reality。

该提交同时移除了 SS 入站生成、SS 凭据回填和订阅分支。旧实现中的 `config.go` skip 和 `nodes.go` 拒绝逻辑都来自这个提交，而不是来自一次 Xray 解析错误或协议实现崩溃。

因此，根因分类是**产品决策叠加访问控制收紧**，不是 Shadowsocks 协议缺陷，也没有证据表明当时存在一个必须通过删除 SS 才能规避的面板安全漏洞。

### 官方协议证据和剩余风险

Xray 官方文档说明 Shadowsocks 支持 TCP 和 UDP，旧 AEAD 方案存在重放保护、可靠性和主动探测方面的历史问题。官方推荐 2022 系列方法，并指出 Shadowsocks 流量不具备 TLS/REALITY 的普通 HTTPS 外观，仍可能被分类识别。[Xray Shadowsocks 入站文档](https://xtls.github.io/en/config/inbounds/shadowsocks.html) [Xray 传输兼容性文档](https://xtls.github.io/en/config/transport.html)

P1 已经规避了面板侧的主要运营风险。

- 节点创建和更新时强制 `tcp`、`none`，清理 Reality、TLS、WS、gRPC 相关字段。
- 只允许白名单加密方式，缺省密码随机生成。
- 订阅导出沿用显式客户节点授权。
- Xray settings 显式设置 `network: "tcp,udp"`，避免服务端默认只监听 TCP。
- P1 保留的协议白名单没有包含官方文档列出的 `2022-blake3-chacha20-poly1305`，这是当前产品范围约束，是否加入需要协调者单独确认。

风险仍然存在。直接暴露的 SS 节点没有 TLS/REALITY 外观，不适合被描述为抗封锁协议。服务端仍应使用强密码、限制安全组来源，并把 UDP 放行和端口暴露当作独立运维风险。

## 二、当前 Xray 安装、Agent 和下发边界

### 安装脚本实际结构

当前仓库的 Xray 安装并不是由 `deploy/install.sh` 自己下载并校验 Xray 压缩包。

- 顶层 `install.sh:162-221` 校验的是面板发布包的 SHA256，并通过 GitHub Release API 找到发布资产。
- `deploy/install.sh:701-702` 调用 `deploy/agent-install.sh`，并把 Xray 相关环境变量传给 Agent 安装脚本。
- `deploy/agent-install.sh:25-56` 优先安装发布包内的 `bin/xray-linux-amd64` 或 `bin/xray`，同时创建 `/etc/yuchen-panel/xray` 和 Xray 默认资源目录。
- `deploy/agent-install.sh:59-75` 在没有内置二进制时调用 Xray 官方社区安装脚本。这里没有面板自有的版本清单和 SHA256 校验闭环。
- `deploy/agent-install.sh:98-108` 写入 `/etc/yuchen-panel/agent.env`。
- `deploy/agent-install.sh:110-123` 写入 `/etc/systemd/system/xray.service.d/99-yuchen-panel.conf`，通过 systemd drop-in 覆盖 Xray 的 `ExecStart`。

因此，sing-box 对称集成不应简单复制一个“看似存在但实际不存在的 Xray SHA256 流程”。协调者需要先决定 sing-box 二进制来源。

### 推荐的 sing-box 安装契约

推荐采用面板自己的版本清单和校验逻辑，或者把 sing-box 二进制作为已校验的发布资产随发行包下发。无论选择哪一种，安装器都应做到以下几点。

1. 固定 sing-box 版本和架构资产，不跟随“latest”漂移。
2. 对下载资产执行 SHA256 校验，校验失败时不覆盖现有运行文件。
3. 安装到 `/usr/local/bin/sing-box`，配置目录使用 `/etc/yuchen-panel/sing-box`。
4. 主配置建议为 `/etc/yuchen-panel/sing-box/config.json`，临时文件使用同目录的 `.tmp.json`。
5. systemd 单元建议为 `/etc/systemd/system/sing-box.service`，核心内容为 `ExecStart=/usr/local/bin/sing-box run -c /etc/yuchen-panel/sing-box/config.json`。
6. systemd 采用 `systemctl restart sing-box`，先执行 `sing-box check -c <temp-config>`，再原子替换配置，最后检查 `systemctl is-active sing-box`。

sing-box 官方文档提供 `sing-box check` 作为配置检查命令，并说明 Linux 安装通常会提供 `sing-box` systemd 服务，服务管理包括 `systemctl restart sing-box`。[sing-box 配置检查文档](https://github.com/SagerNet/sing-box/blob/testing/docs/configuration/index.md) [sing-box 包管理和服务文档](https://sing-box.sagernet.org/installation/package-manager/)

### Agent 双内核配置模型

当前 Agent `Config` 只有一组 Xray 字段。

- `agent/cmd/agent/main.go:62-71` 只有 `ConfigPath`、`TestCommand`、`ReloadCommand`。
- `agent/cmd/agent/main.go:77-86` 只读取 `YC_XRAY_CONFIG`、`YC_XRAY_TEST_CMD` 和 `YC_XRAY_RELOAD_CMD`。
- `agent/cmd/agent/main.go:205-245` 只接受 `XrayConfig`，写一个临时文件，执行一条 test command，再执行一条 reload command。

建议将内核配置抽象成显式的命名对象，而不是继续增加平铺环境变量。

```go
type KernelConfig struct {
    Enabled       bool
    ConfigPath    string
    TestCommand   string
    ReloadCommand string
}

type Config struct {
    PanelBase  string
    ServerID   string
    AgentToken string
    Kernels    map[string]KernelConfig // xray, sing_box
    Interval   time.Duration
    ApplyConfig bool
}
```

环境变量迁移建议如下。

| 内核 | 配置路径 | 检查命令 | 重启命令 |
|---|---|---|---|
| Xray | `YC_XRAY_CONFIG` | `YC_XRAY_TEST_CMD` | `YC_XRAY_RELOAD_CMD` |
| sing-box | `YC_SINGBOX_CONFIG` | `YC_SINGBOX_TEST_CMD` | `YC_SINGBOX_RELOAD_CMD` |

保留旧 Xray 环境变量作为兼容 fallback，新的部署脚本同时写入 sing-box 变量。没有明确启用 sing-box 时，Agent 不应因为缺少 sing-box 二进制而失败。

### Agent 下发协议

当前 `backend/internal/model/model.go:215-223` 的 `AgentSyncResponse` 只有 `XrayConfig`。

建议新增可扩展的内核映射，同时暂时保留 `XrayConfig` 兼容旧 Agent。

```go
type KernelSyncConfig struct {
    Enabled         bool           `json:"enabled"`
    Config          map[string]any `json:"config"`
    DesiredHash     string         `json:"desired_hash"`
    RestartRequired bool           `json:"restart_required"`
}

type AgentSyncResponse struct {
    OK                  bool                        `json:"ok"`
    ServerID            string                      `json:"server_id"`
    DesiredConfigHash   string                      `json:"desired_config_hash"`
    RestartRequired     bool                        `json:"restart_required"`
    XrayConfig          map[string]any              `json:"xray_config"` // compatibility
    KernelConfigs       map[string]KernelSyncConfig `json:"kernel_configs,omitempty"`
    NextIntervalSeconds int                         `json:"next_interval_seconds"`
    Message             string                      `json:"message"`
}
```

Agent 应当按内核独立执行以下事务。

1. 将配置写入对应目录下的临时文件。
2. 执行该内核的检查命令。
3. 所有待更新内核的检查都通过后，再依次原子替换配置。
4. 对每个实际变更的内核执行对应重启命令。
5. 任一内核重启失败时保留 `.reload-pending`，并在 heartbeat 中报告具体内核名。

“全部检查通过后再替换”可以避免 Xray 已更新而 sing-box 检查失败时产生半更新状态。真正的双内核原子提交需要协调者决定是否接受短暂的两个独立 systemd 重启窗口。

## 三、流量统计方案

### 现状

当前 Agent `agent/cmd/agent/traffic.go` 的流程如下。

- `statsAddress` 从 Xray 配置中寻找 `tag=api`、`listen=127.0.0.1` 的 StatsService 端口。
- `parseTraffic` 解析 `user>>>client_<ID>>>>traffic>>>uplink/downlink`。
- `xrayEpoch` 使用 `/proc` 的 boot ID、进程 PID 和 start ticks 组成 epoch。
- `collectXrayTraffic` 执行 `xray api statsquery --server=<loopback> -pattern user>>>client_ -reset=false`，查询前后再次读取 epoch，发现 Xray 在查询期间重启就丢弃本次样本。

这套逻辑依赖 Xray 自带 CLI 和 Xray StatsService 的 JSON 结构，不能直接套到 sing-box。

### sing-box 1.12 V2Ray API 的可行性

sing-box 官方文档提供 `experimental.v2ray_api`。配置必须明确设置 gRPC `listen`，并启用 `stats.enabled`，还可以限制统计的 inbounds、outbounds 和 users。[sing-box V2Ray API 文档](https://sing-box.sagernet.org/configuration/experimental/v2ray-api/)

但官方文档同时明确写出 V2Ray API 默认不包含。上游 issue 记录了即使配置了 `experimental.v2ray_api`，没有对应构建能力时 `StatsService` 仍返回 `Unimplemented`。因此不能把官方默认二进制直接当成已有 Xray StatsService 的替代品。[sing-box V2Ray API 未实现 issue](https://github.com/SagerNet/sing-box/issues/2268)

设计上有两个可选路线。

#### 路线 A，定制 sing-box 构建并复用 V2Ray StatsService

- 采用带 `with_v2ray_api` 的 sing-box 1.12.x 构建。
- 配置 `experimental.v2ray_api.listen` 为 `127.0.0.1:<port>`。
- `stats.enabled=true`，并把需要计量的 inbound、outbound 和 users 写入统计范围。
- 用户名固定为 `client_<ID>`，不能使用客户可编辑的用户名或邮箱，否则客户计费键会变化。
- Agent 使用 gRPC `QueryStats`，验证返回的 stat 名称是否为 `user>>>client_<ID>>>>traffic>>>uplink/downlink`，再决定是否复用现有解析器。
- 首次上线前必须用真实 sing-box 1.12.x 构建做一条双向流量测试。仅凭配置文档不能证明目标构建实际注册了 StatsService。

这条路线最接近现有按客户 ID 计量方案，但有两个已知风险。

1. 官方二进制和定制二进制的 build tags 必须被版本清单、SHA256 和启动日志记录。
2. 上游 issue 记录了 reload 会销毁旧 V2Ray StatsService，尚未读取的计数可能丢失。对计费场景不能直接使用 `systemctl reload` 作为无损假设。[sing-box StatsService reload 数据丢失 issue](https://github.com/SagerNet/sing-box/issues/4059)

#### 路线 B，改用可持久化的外部计量

- **日志解析**只适合诊断，不适合作为按客户计费的主数据源。日志格式、采样和重启边界都可能变化。
- **每客户独立 outbound/inbound**可以让统计键稳定，但会导致配置规模、端口或 tag 数量按客户增长，且 Hysteria2/TUIC 用户模型未必需要为每个客户建立独立监听端口。
- **sidecar 计量服务**可以在 sing-box 前后做流量采集，但需要明确数据路径、重启前 flush 和与 QUIC 多路复用的关联，工程成本最高。

当前建议路线是 A，但必须把“定制构建 + QueryStats 集成测试 + 重启前 flush”作为上线前置条件。若协调者不接受定制 build tag，则 P0 不应承诺 sing-box 侧按客户计费，只能先交付总量或不计费模式。

### sing-box epoch 设计

复用 Agent 的通用进程身份算法，但不要把函数命名绑定到 Xray。

```text
<kernel>:<boot_id>:<pid>:<start_ticks>
```

- `kernel` 区分 `xray` 与 `sing_box`。
- `boot_id` 区分机器重启。
- `pid` 和 `/proc/<pid>/stat` 的 `start_ticks` 区分同一机器上的进程重启。
- 查询前后读取 epoch，变化时丢弃样本并记录边界。
- 重启或配置切换前，先做一次 StatsService flush。若 sing-box reload 会销毁计数器，则应使用 `systemctl restart` 前的显式 flush 和 pending marker，不能只依赖 poll 间隔。

后端 heartbeat 建议最终扩展为按内核区分的结构，例如 `traffic_by_kernel["xray"]` 和 `traffic_by_kernel["sing_box"]`，再由每个客户的绑定节点归属汇总。不要把两个内核的相同 `client_<ID>` 计数直接相加，除非确认它们属于互斥节点集合。

## 四、Hysteria2 与 TUIC 字段清单

### Hysteria2 服务端字段

sing-box 官方 Hysteria2 入站需要 QUIC 监听、用户、TLS，支持带宽、obfs 和 masquerade 等字段。[sing-box Hysteria2 入站文档](https://sing-box.sagernet.org/configuration/inbound/hysteria2/)

建议新增字段如下。

| Node 字段 | 类型 | 作用 |
|---|---|---|
| `Hysteria2Auth` | string | 单用户 auth/password。若未来支持多用户，改为独立凭据表 |
| `Hysteria2UpMbps` | int | 服务端上行带宽 |
| `Hysteria2DownMbps` | int | 服务端下行带宽 |
| `Hysteria2CongestionControl` | string | `brutal`、`bbr` 等产品允许值，需要绑定具体内核版本 |
| `Hysteria2IgnoreClientBandwidth` | bool | 是否忽略客户端带宽声明 |
| `Hysteria2ObfsType` | string | `salamander` 或 `gecko`，空值表示关闭 |
| `Hysteria2ObfsPassword` | string | obfs 密码 |
| `Hysteria2PortHopping` | string | 单端口、逗号分隔端口和范围的原始表达式 |
| `Hysteria2SNI` | string | TLS server name |
| `Hysteria2TLSCertPath` | string | 证书路径或证书引用 ID |
| `Hysteria2TLSKeyPath` | string | 私钥路径或私钥引用 ID |
| `Hysteria2Insecure` | bool | 客户端订阅是否允许跳过证书校验，不应作为服务端默认 |
| `Hysteria2PinSHA256` | string | 客户端证书指纹固定 |
| `Hysteria2Masquerade` | string | 未认证请求的 HTTP/3 伪装目标或静态目录 |

认证、TLS 私钥和 obfs 密码属于凭据字段。若继续放在 `Node` 中，API 返回、审计日志、前端编辑和备份都必须采用现有凭据保护策略。更长期的模型应把 TLS 证书引用和多用户凭据拆到独立表。

### Hysteria2 分享链接

官方 Hysteria2 URI 形式为：

```text
hysteria2://[auth@]host:port/?obfs=salamander&obfs-password=...&sni=...&insecure=1&pinSHA256=...#name
```

官方 URI 文档明确了 `auth`、端口跳跃、`obfs`、`obfs-password`、`sni`、`insecure`、`pinSHA256` 和 `ech` 参数。带端口跳跃时，host 后面的端口部分可使用多端口表达式。[Hysteria2 URI Scheme](https://github.com/HyNetworks/hysteria-website/blob/master/docs/docs/developers/URI-Scheme.md)

带宽和服务端 masquerade 不应放入分享链接。官方文档把这些视为服务端或客户端配置内容，不属于最小连接凭据。

### TUIC 服务端字段

sing-box TUIC 入站要求 users 中的 UUID 和 password，TLS 必需，并支持 `cubic`、`new_reno`、`bbr` 三种 congestion control。官方文档还定义了 auth timeout、heartbeat、zero RTT 和 QUIC 字段。[sing-box TUIC 入站文档](https://sing-box.sagernet.org/configuration/inbound/tuic/)

建议新增字段如下。

| Node 字段 | 类型 | 作用 |
|---|---|---|
| `TUICUUID` | string | TUIC v5 用户 UUID |
| `TUICPassword` | string | TUIC v5 用户密码 |
| `TUICCongestionControl` | string | `cubic`、`new_reno`、`bbr` |
| `TUICAuthTimeout` | string | 例如 `3s` |
| `TUICZeroRTT` | bool | 0-RTT，默认关闭 |
| `TUICHeartbeat` | string | 例如 `10s` |
| `TUICSNI` | string | TLS SNI |
| `TUICALPN` | []string | 例如 `h3` |
| `TUICTLSCertPath` | string | 服务端证书 |
| `TUICTLSKeyPath` | string | 服务端私钥 |
| `TUICInsecure` | bool | 客户端跳过证书验证 |
| `TUICUDPRelayMode` | string | `native` 或 `quic` |
| `TUICNetwork` | string | `tcp`、`udp` 或两者 |

### TUIC 分享链接

TUIC 协议仓库提供协议规范，但没有一个由协议仓库维护的统一 `tuic://` 分享 URI 标准。sing-box 官方文档定义的是 JSON 字段，不是分享 URI。设计阶段可以暂定以下生态兼容形式，但必须由协调者选择目标客户端矩阵后再冻结。

```text
tuic://uuid:password@host:port/?congestion_control=cubic&udp_relay_mode=native&alpn=h3&sni=example.com&insecure=1&reduce_rtt=1#name
```

其中 `uuid` 和 `password` 使用 URI userinfo 编码，`congestion_control`、`udp_relay_mode`、`alpn`、`sni`、`insecure` 和 `reduce_rtt` 需要按照目标客户端实际解析器验证。sing-box 的 JSON 字段证据来自官方 TUIC inbound/outbound 文档。[sing-box TUIC 入站文档](https://sing-box.sagernet.org/configuration/inbound/tuic/) [sing-box TUIC 出站文档](https://sing-box.sagernet.org/configuration/outbound/tuic/) [TUIC 协议仓库](https://github.com/tuic-protocol/tuic)

## 五、建议的分阶段实施

### Phase 0，协调者确认

必须先确认以下选择。

1. sing-box 是否接受 `with_v2ray_api` 定制构建。
2. P0 首个版本是否承诺按客户 ID 计费，还是先只提供连接能力。
3. sing-box 的版本是否锁定 1.12.x，还是允许跟随后续版本。
4. Hysteria2/TUIC 的 TLS 证书由面板、Nginx 还是外部证书系统管理。
5. TUIC 分享链接采用哪一个客户端生态的 URI 规范。
6. 是否接受 sing-box 重启而不是 reload，以及重启期间的流量统计 flush 机制。

### Phase 1，内核和 Agent 抽象

- 增加 `KernelConfig` 和 `KernelSyncConfig`。
- 保留旧 Xray JSON 字段，支持旧 Agent 读取。
- 让 Agent 能独立检查、写入和重启 Xray 与 sing-box。
- 为每个内核定义独立 heartbeat、hash、pending marker 和 epoch。

### Phase 2，安装和 systemd

- 增加 sing-box 固定版本和架构资产。
- 使用 SHA256 校验并记录版本来源。
- 增加 `/etc/yuchen-panel/sing-box/config.json` 和 `sing-box.service`。
- 在部署测试中覆盖缺少二进制、校验失败、配置检查失败和重启失败。

### Phase 3，服务端协议生成

- 先实现 sing-box Shadowsocks 对照配置，验证双内核共存。
- 再实现 Hysteria2 和 TUIC 入站 JSON。
- 证书和用户凭据完成字段校验、备份和审计策略后，再开放前端创建。

### Phase 4，订阅和统计

- 明确 Hysteria2 URI 生成和解析矩阵。
- 明确 TUIC URI 目标客户端和字段损失策略。
- 用实际目标版本的 sing-box 做 `check`、启动、流量、重启、StatsService 查询测试。
- 验证同一客户绑定多个节点时，Xray 和 sing-box 计量不会重复累计。

### Phase 5，灰度

- 先只允许管理员创建 sing-box 节点。
- 先不自动迁移现有客户节点。
- 观察启动失败、统计不可用和重启 pending 状态。
- 协调者确认设计和真实服务器验收后，才进入正式实现批次。

## 六、当前结论

- Shadowsocks 下线是“无消费者”的产品决策，P1 已在显式授权、凭据校验和 UDP 监听方面恢复可控能力，但 SS 仍不具备 TLS/REALITY 的抗分类外观。
- sing-box 可以作为第二内核，但当前 Agent、下发协议和安装脚本都是单 Xray 假设，不能通过增加一个配置文件路径完成集成。
- sing-box V2Ray API 存在构建能力和 reload 丢计数风险。若不接受定制构建，按客户计费应暂缓承诺。
- Hysteria2 字段和 URI 规范证据较完整。TUIC 的 JSON 字段证据完整，但 `tuic://` 分享 URI 需要先锁定目标客户端生态。
- 上述设计必须经协调者确认后才进入业务代码实现。本次 P0 交付不包含业务代码改动。
